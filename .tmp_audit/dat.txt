2. Separação de Responsabilidades — Alembic vs Supabase

O projeto utiliza dois mecanismos de gerenciamento de schema. A tabela abaixo define o que cada um controla. Misturar as responsabilidades — por exemplo, criar tabelas de domínio via painel do Supabase ou tentar versionar as tabelas de Auth via Alembic — resulta em estados inconsistentes difíceis de reproduzir.

Responsabilidade

Gerenciado por

Mecanismo

Tabelas de domínio (provas, movimentações, usuários da aplicação, logs)

Alembic

Migrations versionadas em /migrations/. Executadas via alembic upgrade head no deploy.

Tabelas de autenticação (auth.users, auth.sessions)

Supabase Dashboard

Gerenciadas internamente pelo Supabase Auth. Não tocar via Alembic.

Políticas de Row Level Security (RLS)

Scripts SQL versionados

Mantidos em /migrations/rls/. Reaplicados manualmente após recriação de tabela. Nunca criar RLS exclusivamente via painel do Supabase sem versionamento.

Índices de performance

Alembic

Incluídos nas migrations versionadas junto às tabelas correspondentes.

Seeds de dados iniciais (perfis, configurações padrão)

Alembic

Migration de seed executada uma única vez no primeiro deploy do ambiente.

Regra crítica: toda política de RLS deve existir como arquivo .sql em /migrations/rls/ antes de ser aplicada ao banco. Após qualquer DROP TABLE ou recriação de tabela via Alembic, as políticas de RLS daquele schema devem ser reaplicadas manualmente a partir dos arquivos versionados.

3. Estratégia de Testes

A estratégia segue três camadas complementares, cobrindo desde a lógica de negócio isolada até fluxos de usuário completos no browser. A cobertura mínima de 80% aplica-se à lógica de negócio do backend — máquina de estados, RBAC e regras de cálculo de atraso.
